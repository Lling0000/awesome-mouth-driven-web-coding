# 口喷式 Web Coding 工作流

口喷式不是“写一段很长的 prompt”。它是 **不打字，只对话**：按住右 `Command` 调用千问语音输入，把你要做的事直接说进 Codex、Cos、Claude Code、Cursor、VS Code、ChatGPT 网页、AI 终端或任何能接收文字的 Agent 对话框里，让 AI 执行任务。

Web coding 只是最容易展示结果的场景。真正的核心是：**你的嘴变成键盘，AI 工具变成执行器。**

## 核心循环

```text
聚焦输入框 -> 按住右 Command -> 说任务 -> AI 执行 -> 口述验收 -> 口述修复 -> 口述交付
```

## 第 1 步：把光标放对地方

先打开一个能让 AI 执行任务的地方：

- Codex 对话框。
- Cos / Cursor / VS Code 的 AI 输入框。
- Claude Code 或其它 AI CLI 的终端输入区。
- ChatGPT、Qwen、Claude 网页输入框。
- 任何可以接收文本、再让 AI 做事的工具。

关键不是工具名字，而是：光标必须在你要输入任务的地方。

## 第 2 步：按住右 Command 直接说

千问界面实测提示是：

```text
按住键盘 右 Command 随时随地语音输入
```

你按住右 `Command`，直接说任务。松开后，语音会变成文字进入当前输入框。

## 第 3 步：说“执行型任务”

不要只说想法，要说“你要 AI 怎么干”。

```text
你在当前目录直接执行。
先看一下文件结构，然后创建一个单页网页 demo。
主题是自由职业者时间记录工具。
完成后用浏览器截图检查，手机端不要有横向溢出。
最后总结你改了哪些文件。
```

这比“帮我做个网页”更好，因为它包含上下文、动作、验收和交付。

## 第 4 步：让 AI 先计划，再动手

```text
先给我一个三步计划。
计划确认后你直接开始改文件。
不要问我低价值问题，能从当前目录判断的就自己判断。
```

适合 Codex、Claude Code 这类会读文件、改文件、运行命令的 Agent。

## 第 5 步：继续口述验收

AI 做完之后，不要接管键盘，继续说：

```text
打开预览截图，看页面有没有文字溢出。
检查 README 里有没有运行方式和截图。
运行 git status，确认哪些文件被改了。
```

口喷式的精髓是：连验收也靠对话推进。

## 第 6 步：继续口述修复

```text
移动端标题太挤，只修 hero 区域。
不要重构整个页面。
修完重新截图。
```

好的口述指令通常包含三个元素：

- 问题：哪里不好。
- 边界：只改哪里。
- 验收：改完怎么确认。

## 第 7 步：口述交付

```text
把本次修改提交成一个 commit。
commit message 用 docs: add mouth-driven web coding guide。
然后推送到 GitHub，并验证远端链接能打开。
```

如果工具有权限，AI 会自己执行；如果没有权限，它会把阻塞点告诉你。

## 常用口喷模板

| 目标 | 直接说 |
| --- | --- |
| 让 AI 接管 | `你在当前目录直接执行，先看文件结构，再给三步计划。` |
| 避免废话 | `不要问能从代码里判断的问题，自己检查后继续。` |
| 创建文件 | `创建需要的文件，写完后告诉我路径。` |
| 运行检查 | `运行项目已有测试或最接近的检查命令。` |
| 截图验收 | `打开页面截图，检查有没有遮挡、溢出和空白。` |
| 小步修复 | `只修这个问题，不要顺手重构其它部分。` |
| Git 交付 | `查看 git status，提交并推送，最后给我 GitHub 链接。` |

## 口喷式 Web Coding 的完成标准

一次任务完成时，应该至少满足：

- AI 真的执行了文件修改或命令，而不是只给建议。
- 你主要通过右 `Command` 语音输入推进任务。
- 有可见结果：网页、截图、README、commit 或 GitHub 链接。
- 有验收动作：预览、截图、测试、git status 或远端验证。
